| G4 | CI 已实跑（无远端这一条已关闭）：push 数 = run 数 = 4，修复后 run `39526981564` / `39527171060` 各 5/5 job success | 跨版本/跨平台行为已由 3.11 / 3.13 × ubuntu / windows 四矩阵覆盖；首推暴露的 `--network none` 容器冲突已修 | 已关闭；新增平台随 CI 矩阵扩 |
| G5 | 本机仍无 Python 3.11 通道 | 3.11 特有行为本机验不了 | **已由 CI 覆盖**：`py3.11 · ubuntu` 与 `py3.11 · windows` 两个 job 全步骤 success（M6 实测）；本机仍只跑 3.12 |
| G6 | `ed25519-sha256` 不支持 | 该类签名判不可判定 | 登记为已知限制，看用户反馈 |
| G7 | SPF `exp=` 文本里的 `%{t}` 不展开 | 解释文本缺时间戳（判定结果不受影响） | 本项目判定路径零时钟（K7）；若将来要支持，须改成"时间只取自快照"，届时改 `spf.py::_expand_macro` 与本节 |
| G8 | SPF 与上游有 1 条口径差异（void 超限判 `undecidable`） | 与 pyspf 的 203/203 相比少 1 条一致 | 有意为之，逐条登记；若用户反馈要跟上游，改口径须同时改代码、测试与 `plan/04` §3.1 |
| G9 | DKIM 的 `b=` / `bh=` 失败只给 `kind` + `basis`，不给具体头名/行号 | 用户拿不到「改的是哪个头 / 哪一行」的定位 | `bh=`/`b=` 都是单向哈希，没有原文无法反推；编造行号会把排查带偏。要支持须引入「原件对照」输入（范围外），届时改 `dkim.py` 与 `plan/03` §3.3 |
| G10 | DKIM 的 `x=`（签名过期）不校验 | 过期签名可能被判 pass | 校验过期必须读系统时钟，与 K7 冲突（同 G7）。已改为「必出告警」而非静默忽略；要支持须改成「时间只取自快照」 |
| G11 | DKIM 与 dkimpy 有 2 条口径差异（`l=` 超长判 `permerror`；`rsa-sha1` 判 `permerror`） | 与 dkimpy 逐条对账时这 2 例不一致 | 均按 RFC 判定：`l=` 见 §3.5 MUST NOT + §6.1.1；`rsa-sha1` 见 RFC 8301 §3.1。若用户反馈要跟 dkimpy，须同时改代码、测试与本表 |
| G12 | `i=` 的 AUID 本地部分不做 dkim-quoted-printable 解码 | 含转义字符的 `i=` 会按原样参与域匹配 | 域匹配只用 `@` 之后的部分，本地部分解码不影响判定正确性；要完整支持须在 `dkim.py::_identity_under_domain` 增加解码 |
| G13 | DMARC 的 `np=` 在『快照没查过 Author Domain 本身』时判 `undecidable`（不猜） | 用户会觉得『记录里明明写了 np=，为什么给不出处置』 | `np=` 与 `sp=`/`p=` 在取值不同时给出**不同**处置，猜错一个就是明确的错答案。补抓 Author Domain 的任一类型查询即可判定；`snapshot fetch` 已抓 `_dmarc` 但**不**抓 Author 域本身，需在输入侧补一条查询，届时改 `net.py::plan_queries` 与本表 |
| G14 | `rua=` / `ruf=` 只做 URI **形态**校验，不解析具体方案 | 无法判断接收方是否接受某个非常规 scheme | §4.7 原文『URIs involving schemes not supported by Mail Receivers MUST be ignored』——『支持哪些方案』是实现自由，不属于判定。本工具只用它做 §4.10.1 的兜底判断（有无有效 URI） |
| G15 | DMARC 的 U-label → A-label 转换依赖标准库 `idna` codec | 极端 IDN（如 emoji 域）可能转换失败 | §5.3.1 只要求『convert to an A-label』；转换失败时该域被排除并出告警，不静默丢弃。标准库 codec 不接受 2010 之后的 IDNA2008 规则，要完整支持须引入 `idna` 包（违反零依赖） |
| G16 | 对账只重算 `spf` / `dkim` / `dmarc` 三类 method；`iprev` / `auth` / `arc` 等一律判 `undecidable` | 真实报文里 `iprev=` 很常见，它会一直显示"无法判定" | fail-closed 是刻意的（不猜）；要扩须先定"本工具重算 iprev 的口径"（RFC 8601 §2.7 的 iprev 语义与 SPF 的 HELO 校验不是一回事），届时改 `reconcile.py::_recomputed_result` 与本表 |
| G17 | Received 链只做**单调性与时钟回退**，不做"乱序 / 跳数异常 / 跨时区压缩"的语义分析 | 用户拿不到"这条链看起来被重排过"这类结论 | 首期只做能从字面值直接判定的部分（K21）；更深的分析需要"发信方正常链形态"的基线数据，属新产品面，登记 `docs/backlog.md` |
| G18 | ARC 辅助证据未实现（`plan/02` §5 预留的"恒为 `null` 的 `arc` 键"在实装时**删掉了**） | 没有 ARC 链完整性结论 | 留一个恒为 `null` 的键会让读者以为"查过了、结果是空"，比没有更糟。ARC 是 Experimental 且拟转 Historic，属扩展项，登记 `docs/backlog.md` |
| G19 | SRS 影响模拟未实现；`--change` 只支持 `p` / `sp` / `np` / `t` / `all` / `include` | 名称上写 SRS，实际不支持以 `--change` 表达 | 预留位改为"只做接口说明、不造假成员"（`plan/02` §5）；要支持须先定"SRS 改写后 SPF 域是什么"的口径 |
| G20 | what-if 只改**快照**，不改 `query.json`（`mail_from` / `client_ip` / `helo`） | "换一个发信 IP / 换信封域会怎样"这类反事实做不到 | 初版就定"只改配置不改报文与既成事实"（K22）。要支持须新增 `--change-query` 之类的**独立**开关并写明它与 `--change` 的区别，届时改 `whatif.py::apply_changes` 与本表 |

## 5 决策记录（逐里程碑新增）

| # | 决策 | 备选 | 理由 |
|---|---|---|---|
| D1 | 零运行时依赖（自实现 RSA 原语） | `cryptography` | CI 四矩阵不缺包、发布件自足、离线装包不受代理影响；Ed25519 明确降级为 `undecidable` |
| D2 | `requires-python = ">=3.11"` | 降到 3.9 | 照题面 §1；本机 3.12 通道开发，3.11/3.13 由 CI 覆盖 |
| D3 | **M0–M5 不建远端，M6 才建**（已按此执行：M6 建仓并首推） | M0 就 `gh repo create` | 前几棒只交付"计划 + 骨架/判定"，脱敏四步属发布棒；未脱敏就公开会让 `fixtures/` 的真实域风险外泄 |
| D4 | 平铺 `mailvault/` 而非 `src/` | `src/` 布局 | 题面 §8 目录约定是规格 |
| D5 | argparse `SystemExit(2)` 统一转 3 | 保留 2 | 与 `undecidable` 的退出码 2 语义冲突 |
| D6 | 未实现子命令返回 `MODULE_NOT_READY` + exit 2 | 直接报错/静默成功 | fail-closed；"没做"不能长得像"通过" |
| **D7** | **矛盾在账本里的汇总结果是 `undecidable`，不是 `fail`** | 映射成 `fail` | 矛盾的真实含义是"我不知道哪一侧描述的是现实"（题面风险 ③：极易被读成"你被黑了"）。`fail` 在本项目里是"判定为失败"，与"判决不了"是两种结论（K19） |
| **D8** | **禁词表提到 `constants.py`，`render.py` 只引用不再自定义** | 两处各写一份 | 对账要在**装配期**自检自己生成的解释里有没有定性词，渲染期是第二道闸。两处各写一份必然漂移，而 drift 的方向恰好是"渲染通过、解释里写着定性词"（K24） |
| **D9** | **卫生门剥掉 RFC 8601 的 `ptype.property=` 前缀，而不是改 fixture 绕开** | 把 `smtp.mailfrom=` 从 fixture 里删掉 | 删掉会降低 fixture 保真度（读者看不到"收件方评估的是哪个信封发件人"）；"改数据去迁就门"会让门慢慢失去意义。剥前缀 + 阴性对照（`plan/04` §3.6） |
| **D10** | **判定逻辑另有变异验证脚本**（`tools/verify_module_mutations.py`），并要求植入后文件**仍能编译** | 只跑正常测试 | 语法类 AST 守门抓不到"跳步漏了""fail-open 了"这类语义故障；而"语法错导致 pytest 红"是假红，必须排除（`plan/05` §3 的 11 组） |
| **D11** | **归档样例用真 CLI 跑真 fixture 生成**（`tools/gen_examples.py`），`--check` 同时断言逐字节幂等与**退出码未漂** | 手搓示例 JSON | 手搓的样例会随渲染层漂移，而它们恰恰是"输出长什么样"的对外凭证；退出码漂移意味着"样例展示的结论"与"当前实装"已经不是一回事 |
| **D12** | **卫生门扫 `fixtures/` + `examples/`**，并新增两条**结构性剥离**（标识符命名空间闭集 + RFC 引用） | 只扫 `fixtures/`；或把 `dmarc.evaluate` 之类塞进白名单 | 输入与输出都是对外凭证。剥离**只去前缀**、剩余部分照旧被扫（`walk.mail.google.com.0` 仍报红），且闭集外不剥（fail-closed）；白名单写法会随命名空间增长而漏 |
| **D13** | **发布门分三态**（`--offline` / `--pre-tag` / `--online`），CI 只跑 `--offline` | 一条门判全部 | 每条判据只在**它确实成立的那一态**才是判据：`--pre-tag` 在 tag 推送那一刻必然假红，`--online` 需要远端状态 |
| **D14** | **离线 job 用 `docker run --network none` 嵌套容器**，不写 `container.options: --network none` | 保留 job 容器写法 | Actions 给 job 容器挂 user-defined network，与 `--network none` 互斥（`docker: conflicting options`，实测 run `39526291036`）。本机无 docker，缺陷只在远端显形 |
