## 2 CLI 契约（M0 冻结）

冻结子命令（题面 §8）：`snapshot fetch` / `audit` / `whatif` / `diff`。
新增子命令必须先写 `docs/backlog.md`。

```
mailvault [--version] <command> ...

mailvault snapshot fetch --eml <path> --query <path> -o <snap.json>
                          [--resolver <name>] [--psl <path>]

mailvault audit  --snapshot <snap.json> --eml <message.eml> --query <query.json>
                 [--json <out.json>] [--md <out.md>] [--strict-evidence] [--out-dir <dir>]

mailvault whatif --snapshot <snap.json> --eml <message.eml> --query <query.json>
                 --change <key=value> [--change ...] [--json ...] [--md ...]

mailvault diff   --baseline <verdict.json> --candidate <verdict.json> [--json ...] [--md ...]
```

**参数语义三条（M0 起就锁死）**：

1. `--change` 是**可重复**参数，不是逗号分隔（`--change p=reject --change t=y`）。
   文档与 parser 必须一致——`add_argument(action="append")`，**不加** `choices=`。
   若某天要支持逗号，必须同时改 README 与解析器，并加一条"文档 → parser 反射对账"测试。
2. 输出位置：`--json` / `--md` 是**文件路径**；`--out-dir` 是目录，给未指定路径的产物兜底。
   两者同时给时 `--json`/`--md` 优先，`--out-dir` 只影响默认文件名。
3. 未知 `--change` 键或不可解析的值 → `InputError`（exit 3），**不做静默忽略**。

**M5 实装后补齐的两条（都写进 `--help`）**：

4. `--change` 的键与取值（`constants.WHATIF_CHANGE_KEYS` / `WHATIF_SPF_ALL_VALUES`）：
   `p=` / `sp=` / `np=` 取 `none|quarantine|reject`；`t=` 取 `y|n`；`all=` 取
   `+all|-all|~all|?all`；**`include:<domain>` 用冒号**（`plan/03` §2 冻结的形态就是冒号，
   `include=<domain>` 是同一件事的另一种写法，一并接受，不引入第二种语义）。K25。
5. `--strict-evidence` 在 `whatif` / `diff` 上**也可用**（M5 起）：对账解释与差分报告
   同样会被归档，禁词口径不该只覆盖 `audit`。K24。

**默认行为**：`audit` / `whatif` 不给输出参数时，把 `verdict.json` + `verdict.md` 写到
`--out-dir`（默认当前目录）；`diff` 写 `diff.json` + `diff.md`——**不覆盖** `verdict.*`：
"diff 把 verdict.json 盖掉"会让用户丢掉基线账本。
`--json -` 表示写 stdout（仅 JSON 轨道，便于管道）。

**`diff` 的退出码是 `0`**：它是**比较**命令，"有差异"是它正常的输出，不是失败。
映射成 `1` 会与本项目"`1` = 存在 fail"的语义撞车。

## 3 各模块详设

### 3.1 `snapshot.py`（M1）

`snap.json` 结构（与 `plan/01` §4 一致）：

```json
{
  "schema_version": 1,
  "fetched_at": "2026-10-19T18:35:00Z",
  "resolver": "synthetic",
  "psl_version": "2026-10-01",
  "psl_date": "2026-10-01",
  "queries": [
    {"qname": "_dmarc.example.invalid", "qtype": "TXT", "rcode": "NOERROR",
     "answer": ["v=DMARC1; p=none; rua=mailto:dmarc@example.invalid"], "ttl": 300}
  ]
}
```

**关键语义**（题面要求"逐查询 qname/qtype/rcode/answer/ttl"）：

- `queries` 是**有序列表**，不是字典——同一 `(qname,qtype)` 可有多次查询（CNAME 链、重试）。
- 查询接口 `Snapshot.resolve(qname, qtype) -> Resolved` 返回**第一次命中的那一条**（按列表顺序），
  并把命中下标写进 `trace`。这样"快照里查了两次结果不同"这种真实情况不会被静默掩盖。
- `rcode` 非 `NOERROR`（如 `NXDOMAIN`）时 `answer` 必须为空列表；不满足 → `InputError`。
- 缺 `psl_version` / `psl_date` → `InputError`（题面 §2.5 灰区 3 要求输出必须带）。
- 未知 `schema_version` → `InputError`，错误信息列出支持版本。

### 3.2 `modules/spf.py`（M2）

**核心接口**：

```python
def check_host(snap: Snapshot, ip: str, domain: str, helo: str | None, *,
               budget: Budget, trace: Trace) -> SpfResult
```

**预算账本**：`Budget` 是可变对象，每消费一格 `consume(kind, node_id)` 记
`(kind, node_id, ref)`；超限时**不抛异常**，而是在结果上标 `limit_hit`（并记下是哪几格），
由求值层决定后果：

| 格 | 超限后果 | 依据 |
|---|---|---|
| `terms`（DNS 查询类 term 全局计数） | `permerror` | RFC 7208 §4.6.4 MUST |
| `mx`（单次 MX 返回条数） | `permerror` | 同上 MUST |
| `ptr`（单次 PTR 返回条数） | **截断到前 10 条**，不判错 | 同上："超出前 10 条 MUST 被忽略"（`plan/04` §3.1 C1） |
| `void`（空答复次数） | `undecidable` + 告警 | 原文是 SHOULD；题面 §2.5 灰区 2（`plan/04` §3.1 C2） |
| `depth`（include/redirect 嵌套） | `permerror` | 本项目第二道保险，防递归栈跑穿 |

**MUST 优先**：同一条记录同时踩 MUST 与 SHOULD 时报 MUST——那条记录无论实现怎么选都是坏的。
实现上 `void` 超限只**置位**（`ctx.void_exceeded`）、不提前返回，由求值结束处统一裁决。

**include 树**：完整展开，**不因第 11 个 term 截断**（截断的树会把"后面还有 N 个 include"
藏起来，那正是用户想看的）。每个节点带 `domain` / `record` / `child_result` /
`consumes_term` / `receiver_would_stop_here`（第 11 个起为 true）/ `terminates_parent`。
节点 id 规则：根 `n0`，第 i 个 include 子节点 `n<i>`，嵌套 `n<i>.<j>`（K12）——
**只由路径决定**，与遍历顺序、与是否被截断都无关。

**树不进判定**：画树用独立的 shadow 上下文（独立预算、独立缓存）。否则"为了画树"的
查询会污染 void 计数与 term 预算，判定就不再可复算。

**数据缺口 ≠ 没有记录**（`plan/04` §2.3）：`Snapshot.resolve()` 返回 `found=False` 时
结果带 `data_gap=(qname, qtype)` 且判 `undecidable`，**绝不**落到 `none`。
`data_gap` 与 `undecidable` 分开：前者是"待补的输入"，后者是"已经得出的结论"。

**RFC 7208 测试集接入**：`fixtures/spf/rfc7208-tests.yml`（pyspf 原始文件，保留 LICENSE）。
`tests/rfc7208_suite.py::run_case()` 把 yml 里的 `dns` 桩转成合成 `Snapshot`，逐条跑
`check_host()`；宏展开后的查询名事先算不出来，所以按"求值器报缺口 → 补进快照 → 重跑"
迭代到收敛（每一步的查询都是**桩真实答复过的**，不是猜的）。**
203 用例通过率 99.5%（202/203）**；失败逐条登记 `data/rfc7208-failures.md`，
且该登记表由 `tests/test_spf.py` 三条断言盯着（缺条目 / 僵尸条目 / 没写通过率都报红）。

### 3.3 `modules/dkim.py`（M3）

**多签名**：遍历 `DKIM-Signature` 头**全部**条目（同名头可重复），逐条独立求值，不短路。
每条输出 `selector` / `d` / `i` / `a` / `c` / `bh_matches` / `failure_at` / `key_bits` / `key_status` / `result`。

**`failure_at` 定位**（M3 实装口径，比初版更严）：
**只在能判定时才给确切位置，判不了就明说判不了**——`kind` 必给，`header` / `offset` /
`body_line` 在不可判定时为 `null`，并附 `basis` 说明为什么。

| `kind` | 何时出现 | 定位字段 |
|---|---|---|
| `header_syntax` | 标签语法错、`v=` ≠ 1、`c=` 非法、`a=` 形态错、`bh=` 非 base64 | `header` + `offset`（标签在头值里的字节偏移） |
| `missing_tag` | 缺 §3.5 列为 REQUIRED 的标签 | `header` + `tags`（缺了哪些） |
| `domain_mismatch` | `i=` 不在 `d=` 之下 | `header` + `offset` |
| `from_not_signed` | `h=` 不含 `from` | `header`（=`From`） |
| `length_exceeds_body` | `l=` > 规范化正文长度 | `header` + `offset` + `body_line`（=1）+ `limit` + `canonical_length` |
| `body_hash` | `bh=` 不匹配 | `body_line: null` + `basis`（单向摘要，无原文无法反推行号） |
| `header_hash` | `b=` 验签不过 | `header: null` + `basis`（同上，无法反推是哪个头） |

**为什么初版的 `{"body_line": <int>}`（"规范化后第一处不匹配的行"）做不到**：`bh=` 与 `b=`
都是对整段输入的**单向哈希**，验签器手上只有"匹配 / 不匹配"一个比特，没有"哪一行不同"
这个信息——那是签名者才有的（他手上有原文）。若硬要输出行号，只能靠启发式（比如逐行
剔除后重算哈希），代价是 O(n) 次哈希且结论不可靠。本项目选择**如实说不可判定**而不是
给一个看起来精确、实际会误导排查方向的行号。要支持须引入"原件对照"输入（`plan/06` G9）。
唯一能确切给行号的情形是 `l=` 边界——"从第几行起未受保护"是可判定的，已作为告警输出。

**`key_status`**：`ok` / `revoked`（`p=` 为空）/ `missing` / `weak`（<1024 位）/ `invalid`
（记录在但不可用：语法错、`k=` 非 rsa、`h=` 排除该哈希、`s=` 不含 email）。
`missing` 分两种，**结论不同**（K13）：快照没查过 → `undecidable` + `data_gap`（待补输入）；
快照明确答复 NXDOMAIN/空 → `permerror`（§6.1.2 第 3 步）。
`weak` → `fail`（RFC 8301 §3.2 是 MUST）。`None` 表示"没走到取密钥那一步"。
`a=ed25519-sha256` → `undecidable` + 告警「本工具不支持该算法」（见 `plan/02` §4）。

**步骤顺序照 RFC 6376 §6.1 原文**：§6.1.1 校验签名头 → §6.1.2 取密钥 → §6.1.3 算哈希与验签。
不把"取密钥"挪到"算正文哈希"之后：密钥已撤销 + 正文也被改时，后者会把"密钥已撤销"
这条独立事实藏起来。

**`a=rsa-sha1`** → `permerror`。RFC 8301 §3.1 把它从"必须支持"改成
"MUST NOT be used for signing or verifying"，并指出这类签名 "have permanently failed
evaluation"。dkimpy 仍会算出密码学结果，本项目按 RFC 判永久失败（差异登记 `plan/06` G11）。

**`l=` 大于规范化正文长度** → `permerror`。§3.5 是 "MUST NOT be larger"，
§6.1.1 要求任何不一致的取值立即 PERMFAIL；dkimpy 用 `body[:l]` 静默取全量（差异登记 G11）。

**判定路径零时钟**（K7）：`t=` / `x=` 不参与判定，`x=` 存在时**必出告警**（`plan/06` G10）。

### 3.4 `modules/dmarc.py`（M4，✅ 2026-10-21）

**tree walk 照 §4.10 的通用步骤 1–7 实现**，不是"从 Author 域逐级往上找 `_dmarc`"。
两者的差别在**标签数 ≥ 8 时的跳步**：§4.10 步骤 4 要求 "remove the left-most labels
until 7 labels remain"，于是 13 标签的 Author 第二跳直接落到 7 标签处（B.4.2 原文的
"skipping the intermediate names"）。漏掉跳步的实现在深域名上会多做几十次查询，
且与附录逐跳结果对不上——所以测试断言的是**逐跳 qname 序列**，不是"最终结论对上了"。

**走查一直走到标签用尽或遇到 `psd=n`/`psd=y`**，不早停：§4.10.2 的 Organizational
Domain 选择要按"从长到短"看**全部**命中记录。早停会让 `psd=y` 形态选错答案。
§4.10.1 的策略**偏好**顺序（Author → Org → PSD）由 `_discover_policy()` 在这份完整
走查结果上施加。

**§4.10.2 的三段选择**（逐条对应原文）：

| 顺序 | 条件 | Organizational Domain |
|---|---|---|
| 1 | 有效记录带 `psd=n` | 该域**本身** |
| 2 | 有效记录带 `psd=y` **且不是走查起点那条** | 该域**下面一层**（B.4.3） |
| 3 | 否则 | **标签最少**的那条记录的域（B.4.1/B.4.2） |

一条记录都没有 → `None`，relaxed 对齐因此不可能成立（**不**退回"起点即 Org 域"，
那会把 `none` 与 `pass` 混起来）。

**单跳状态**（`constants.DMARC_WALK_STATUSES`，判定顺序即错误优先级）：
`not_queried`（数据缺口，K13）→ `dns_error`（§5.3.6）→ `nxdomain` → `no_record` →
`invalid_record`（`v=` 不合格，整条忽略）→ `multiple_records`（§4.10 步骤 2：
同一目标多条**全部丢弃**）→ `record`。

**双算对齐**：`spf_align` / `dkim_align` 各出 `relaxed` 与 `strict` 两个布尔值，
**不合并**——诊断时两者差异本身就是信息。`adkim=` / `aspf=` 各自只影响自己那一侧
（SPF 用 `aspf`，DKIM 用 `adkim`），互不交叉。

**SPF 身份只认 MAIL FROM**（§4.4.2 原文 "DMARC relies solely on SPF validation of the
MAIL FROM identity"）。但**空反向路径不是"没有身份"**：§3.2.4 把 SPF 域定义为
"an SPF-validated MAIL FROM identity" 并指向 RFC 7208 §2.4——那里写的是
"When the reverse-path is null ... the 'MAIL FROM' identity [is] the mailbox composed
of the local-part 'postmaster' and the 'HELO' identity"。所以 `MAIL FROM:<>` 时
**SPF 域就是 HELO 域**，仍是一个 Authenticated Identifier。只有 HELO 也为空时才真的
没有 SPF 身份。

> 这条是 M4 实装后**更正**的：初版按"空发件人 → 无身份"实现，会把这类报文的 DMARC
> 判得比 RFC 严（本该 relaxed 对齐判 pass，却判 fail）。`plan/HANDOFF-M4` §三第 2 条
> 写的"SPF 侧用 MAIL FROM 域（或 HELO 域）"其实是对的那个方向，实装时漏了括号。

**DKIM 身份逐条算**（§4.4.1）：每条 `pass` 的签名各是一个 Authenticated Identifier，
任意一条对齐即满足；不对齐的也逐条留痕。

**处置选择**（§4.10.1）：Author 自己的记录 → `p`；子域**存在** → `sp`（无则 `p`）；
**不存在** → `np`（无则 `sp`，再 `p`）。`p` 缺失 → §4.7 按 `p=none`。值非法 →
有有效 `rua` 则按 `p=none` 继续，否则"不施加 DMARC 处理"（`disposition_status` 为
`not_applicable`）。

**`np=` 的存在性歧义**：记录带 `np=`，但快照里没有 Author Domain 本身的查询 →
`disposition_status = "undecidable"`、`disposition = null`。用 `sp=` 顶上会给出一个
"看着确定"的错答案。例外：`np=` 与 `sp=/p=` 折算出的处置**相同**时不算歧义
（结论一样），此时判 `determined` 并出告警说明。

**`t=y`**（§4.7）：处置降一级 `reject`→`quarantine`、`quarantine`→`none`、`none` 不变；
降级必进 warnings，否则读者看到的处置与记录里的 `p=` 对不上。

**旧标签告警**：`pct` / `rf` / `ri` 出现即 `warnings` 追加"已被 RFC 9989 删除"
（C.5.2，`pct` 另见 A.6），**不得静默忽略**（题面 M3 验收 2）。三者**不解释语义**：
`pct=0` 不会让策略变成 `none`——那正是"静默采纳已删除语义"。`psd` / `np` / `t` 正常
解析并进输出。未知标签按 §4.7 "unknown tags MUST be ignored"，
**不告警**（那是协议明确允许的扩展位）；已删除的标签不重复报成"未知标签"
（同一事实报两次会让读者以为是两个问题）。

**PSL 版本与口径**：输出必带 `psl_version` + `psl_date`，**来自快照**；与随包冻结件
版本不同时出告警。`organizational_domain` **只**由 tree walk 得出；
`psl_organizational_domain` 是**对照值**（来自 PSL 冻结件）。两者在 `psd=y` 场景下
必然不同——把 PSL 值当判定值会在 B.4.3 形态下判错。

**`data_gap` 与 `undecidable` 分开**（K13，与 SPF/DKIM 同一口径）：`not_queried` 的跳
进 `data_gaps`（待补的输入），整条结论 `undecidable`；快照答复 `NXDOMAIN` 是"问过了
没有"，走查继续。

**退出码不自算**：`dmarc.py` 只给 `result`；退出码仍由 `ledger.summary.exit_code`
（= `exits.exit_code_for`）从全部 `checks[]` 算出。

### 3.5 `modules/reconcile.py`（M5，✅ 2026-10-21）

**对账对象**：报文里的 `Authentication-Results`（RFC 8601）**vs** 本工具在同一份快照 +
同一份 `query.json` 上重算出来的 SPF / DKIM / DMARC 结论。

**三分类**（`constants.RECONCILE_CLASSES`）：

| 分类 | 何时 | 附带什么 |
|---|---|---|
| `consistent` | 人工可信的 authserv-id 下，claimed 与 recomputed **相等** | — |
| `contradiction` | 可信且两侧都可比，但**不相等** | **≥ 2 条**解释（`constants.RECONCILE_MIN_EXPLANATIONS`），每条带 `hypothesis` + `verify`（具体要查什么） |
| `undecidable` | 判不了（三类情形，全部 fail-closed） | `warnings` 写明为什么判不了 |

`undecidable` 的三类情形：① authserv-id 不在 `trusted_authserv_ids` 里；② authserv-id 或整条
`Authentication-Results` 不可解析；③ 重算侧给不出可比结论（本工具不重算该 method、
`d=<X>` 的签名在报文里不存在、重算结果本身是 `undecidable`）。

**AR 解析照 RFC 8601 §2.2**：`authserv-id [version] ; method=result (reason) ptype.property=value`。
三条原文口径进了测试：authserv-id 之后的整数是**版本号**而不是名字的一部分；
`method` 后不带 `=` 时 result 默认 `none`；`(reason)` 里可以出现 `;`——按顶层分号切段的
实现会在这里切错。**解析失败不抛异常**，而是产出一条带 `parse_note` 的 `Claim`，
让它变成一条 `undecidable` 结论：一条坏头不该炸掉整份账本，它该让读者看见
"这里有一张头，我看不懂，所以它不算证据"。

**`to_check_entry()` 汇总成一条** `reconcile.cross_check`：全一致 → `pass`；出现矛盾或
判不了 → `undecidable`；一个 AR 都没有 → `none`（K19）。**没有**把矛盾映射成 `fail`
——那正是题面风险 ③ 要避免的误读。汇总条目进 `checks[]`，所以对账的灰区会让退出码变 2，
但**永远不会**让退出码变 1。

**`received_chain()`**：`monotonic` / `clock_regressions` / `hop_count` / `unparsed_dates`
/ `dates`（进 `trace`）。`Received` 由收件方**前插**（RFC 5321 §4.4），所以物理顺序是
最新在前，沿列表往下时间应**不递增**；任何"往下走反而更新"逐处登记。
时间**只取字面值、只做相互比较**，解析不出或没时区偏移 → `monotonic = null`（K21）。

**双解释不是模板**：`_hypotheses()` 按 (method, claimed, recomputed) 与**现场证据**
（`mail_from` 域 vs `From` 域、Received 跳数、DKIM 的 `failure_at.kind`、报文里实际存在的
签名域）生成，例如"网关在验签之后重写了正文"只在 `failure_at.kind == body_hash` 时出现。
`_reconcile_one()` 里有一条自检：`contradiction` 而解释数 < 2 → `InternalError`
（不变量写进代码，不靠"我记得要写两条"）。

### 3.6 `modules/whatif.py`（M5，✅ 2026-10-21）

**做法**（题面 §3 的 M5 明文要求）：**不重写求值器**。`apply_changes()` 把 `--change`
施加到快照的**深拷贝**上，再让**同一套** M2–M4 求值器跑一遍。`cli._run_checks()` 是
`audit` 与 `whatif` 的**共用入口**——两边各写一份"怎么调求值器"必然漂移，而 whatif 的
全部意义就是"与 audit 用同一套求值器"。

**改什么、不改什么**（K22）：只改**快照副本**。`.eml` 与 `query.json` 是**既成事实**，
反事实要问的是"配置改了会怎样"，不是"报文改了会怎样"。

| 键 | 目标记录 | 改法 |
|---|---|---|
| `p` / `sp` / `np` / `t` | `_dmarc.<author>`（Author 域对不上时退化为"唯一一条带 DMARC 记录的 `_dmarc` 查询"；多于一条且对不上 → `InputError`，**不挑一条来猜**） | 设置/追加标签，**其余标签原样原序** |
| `all` | `spf_domain` 的 `v=spf1` 记录 | 替换 `+all/-all/~all/?all` 之一；没有 `all` 则追加 |
| `include` | 同上 | 插在 `all` **之前**（`all` 之后的机制永远走不到） |

目标记录不存在 → `InputError`：**不凭空造记录**（`plan/04` §2.3）。

**差分可复算**（`diff_ledgers` / `apply_ops` / `invert_ops`）：

- ops 的语义是"施加到基线得到候选"，反转后施加到候选得到基线——**两个方向都有断言**，
  且用的是**两份独立的 CLI 产物**（`audit` 给基线、`whatif` 给候选）。
- 列表只在"等长且元素都是对象"时按下标递归；**长度不同就整表当一个值**——按下标做增删时
  重建顺序无法唯一定义，那个洞比"差分粒度粗一点"严重得多。
- 产物里另有 `changed_checks`（人读用：哪些 `check_id` 的哪些字段变了），但它**不参与**
  可逆性——可逆性只由 `ops` 保证。
- `whatif` 块是**报告信封**：它描述的是两份账本，所以不参与差分、也不参与 `ledger_id`
  （否则自指）。

**RUA 关联**（`rua_association`）：吃 `fixtures/whatif/rua.json` 形态的最小报告，按
`identifiers.header_from` + `source_ip` 聚类，列出"策略取 `p=reject` 时会打断谁"——
**口径是"SPF 与 DKIM 都没有通过对齐"**（任一通过即对齐成立，不会被 `reject` 打断）。
输出必须带 `period_note`：**只覆盖报告期内，且依赖报告方的观测口径**（source_ip 取样点、
对齐判定实现），这与"本次审计这一时刻"不是一回事。
缺 `--rua` → `status: "undecidable"` + `required_inputs`（K23），**不猜**；
给了 `--rua` 但路径不存在 / JSON 坏 → `InputError`（那是路径写错，不是"没有数据"）。
`--rua` 缺省**不影响退出码**——退出码仍由 `checks[]` 经 `exit_code_for` 算出。

## 4 错误与边界

| 情况 | 处理 | 退出码 |
|---|---|---|
| 文件不存在 / 不可读 | `InputError`，消息含相对路径 | 3 |
| JSON 语法错 | `InputError` + 行列号 | 3 |
| `schema_version` 不支持 | `InputError` + 支持版本列表 | 3 |
| `.eml` 无 `DKIM-Signature` | 不是错误：`dkim` 判定为 `none`，其余照常 | 按其余结果 |
| 快照缺必需的 key 记录 | `undecidable`（不是 `fail`） | 2 |
| 未捕获异常 | `InternalError`，**打印栈**，不吞 | 4 |
| 参数错（argparse） | `SystemExit(2)` → **CLI 入口统一转成 3**（输入错误） | 3 |

> 最后一条是刻意统一：argparse 默认 `exit 2` 与 `undecidable` 的 `2` 语义冲突。
> 入口捕获 `SystemExit(2)` 并转 3，测试锁定这一行为（`test_contract.test_argparse_exit_code`）。
