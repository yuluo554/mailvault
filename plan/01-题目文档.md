**定位宣言（原文照录，产品文案不得改写其边界）**

> `checkdmarc` 管记录健不健康，`mailauth` 管这条消息能不能过，`parsedmarc` 管历史上谁在发——**没人把三者放在同一份 DNS 快照上对账，并给每条判定挂 RFC 条款与求值轨迹**。本工具做的是可归档的判定账本，不是又一个 SPF 检查器，也不承诺邮件进箱。

两条显式否定，写进 README 首屏与 `--help` 尾注：

- **不承诺进箱**：本工具不输出"进箱概率"，不做内容打分，不做发信测试。
- **不卖"离线"**：离线重放本身不是差异化卖点（`mailauth` 的 `report --dns-cache` 已能离线重放）。卖点是**条款级账本 + 三方对账 + what-if 差分**。

## 2 介绍

### 2.1 三工具的分段边界（已读源码/文档核实）

| 工具 | 覆盖到哪 | 明确没覆盖到哪 |
|---|---|---|
| **mailauth**（postalsys）| `authenticate()` 全做 SPF/DKIM/DMARC/ARC/BIMI；CLI `report --dns-cache dns.json` **已能离线重放**；已支持 RFC 9989 §4.10 tree walk | 输出面向"这条消息过不过"，不做多来源交叉对账，不把判定逐格挂到 RFC 条款与求值轨迹上 |
| **checkdmarc** | SPF 记录校验 + lookup/void 计数、DMARC（含 RFC 9989 `psd`/`np`/`t` 与 tree walk）、BIMI、MTA-STS、TLS-RPT、DNSSEC | **不做 `check_host()`**（只有 ptr_match 辅助）；**CLI 无离线输入**；不读 `.eml`；不做 DKIM 验签；输出是 JSON 事实不是条款账本；issue #172 用户想看完整 include 总量而非在第 11 次停下 |
| **pyspf** | 完整 `check_host()`、10 lookup + 2 void 限制、**自带 RFC 7208 测试集（203 个 `spec:` 用例、16 分组）**、DNS 层可替换 | 无 CLI；无报告；不做 DMARC |
| **dkimpy** | DKIM/ARC/TLSRPT，`verify(dnsfunc=...)` 可注入 | 纯库，零 CLI |
| **parsedmarc** | RUA/RUF 解析（已支持 RFC 9990/9991）、IMAP/Graph 拉取、ES 投递 | **只解析报告，不评估配置** |
| **OpenDMARC** | milter 运行期判定 | 不做事后审计 |
| **rspamd** | MTA 插件 | 非审计器，评分不可离线复算 |
| **Zonemaster / DNSControl** | DNS 健康测试 / IaC | 与本题有重叠但不做报文级判定 |
| **MailVerity（0★）/ Edict（1★）/ Herald（1★）** | 离线 DNS fixture、RFC 9989 标签、simulate 对齐模拟 / 离线 PyQt6 "永不联网" | Edict 明说 "follows no `include:` chain"；均未形成条款账本与三方对账 |

### 2.4 RFC 条款（已核对原文）

- RFC 7208 §4.6.4：10 次 term 限制，第 11 个 → permerror；MX/PTR 各最多 10 条；void lookup SHOULD 上限 2。
- RFC 7208 §4.5：0 条记录 → `none`；多条 → permerror。
- RFC 7208 §5.2：`include` 对子域做 `check_host()`，结果不是文本拼接；被引用记录的 `-all` 不终止整体处理。
- RFC 7208 §6.1：`redirect` 仅在无机制匹配时生效。
- RFC 7208 §7：宏。
- RFC 6376 §3.4 规范化；§3.5 `l=` 不得大于规范化正文长度。
- RFC 8301 §3.2：<1024 位 RSA **必须**判无效。
- RFC 8601 §2.5 / §4.1 / §5 / §7.1：`authserv-id` / 外来 AR 应删 / 伪造头。
- RFC 5321 §4.4、RFC 5322 §3.6.7：Received 前插顺序。
- RFC 9989 §4.10 / §4.10.1（DMARC 策略发现顺序 Author → Org → PSD）、§4.10.2（对齐）、§3.2 标签表（含 `t`/`np`/`psd`；`pct`/`rf`/`ri` 已标 historic）、Appendix C.5.2 / C.6 与 §7.4。
- ARC：RFC 8617 为 Experimental，另有 arc-to-historic 草案。

### 2.5 灰区（必须显式输出 `undecidable`）

1. **进不进垃圾箱**：声誉/IP 预热/内容打分/收件人互动/Gmail·MS 未公开规则。HN 45479279 满分仍被拒是铁证。**不得给"进箱概率"**。
2. **void lookup 是 SHOULD**（RFC 7208 §4.6.4），不是 MUST。
3. **PSL 版本影响 Organizational Domain** → 输出须带 PSL 版本与日期。
4. **`%{p}` 依赖 PTR**，缺 PTR 必须 `undecidable`，不得默认 fail。
5. **ARC 是 Experimental**（RFC 8617）且有 arc-to-historic 草案 → 只报"链是否密码学完整"，不报"会被采信"。

## 3 任务要求

统一约定（五模块共用，写进 CLI `--help` 与 README）：

- **输入三件套**：`snap.json`（DNS 快照）、`message.eml`、`query.json`（mail_from / client_ip / helo / 可信 authserv-id 列表）。
- **输出**：`verdict.json`（机器可复算）+ `verdict.md`（人读账本）。所有判定带 `evidence_ref` 指向 RFC 条款与求值轨迹节点。
- **确定性纪律**：不读系统时钟做判定、不读真实 DNS、不随机、字典键序固定、浮点与时间全部格式化、两次运行字节级一致。时间戳只能来自快照元数据。
- **退出码一处定义**：`0` 全 pass/none、`1` 存在 fail、`2` 存在 undecidable、`3` 输入或快照错误、`4` 内部错误（不得吞异常）。
- **网络纪律**：除 `snapshot fetch` 外，进程内不得打开 socket；CI 用断网容器跑全部测试。

---

### M1 SPF `check_host()` 确定性求值 + 预算账本

**输入**：`snap.json`、`mail_from`、`client_ip`、`helo`。
**输出**：
- `result`：`none` / `neutral` / `pass` / `fail` / `softfail` / `temperror` / `permerror`。
- `budget`：逐格消耗账本（term 数、MX 条数、PTR 条数、void lookup 数、`include`/`redirect` 嵌套深度），每格标"已用/上限/条款号"。
- `tree`：**完整 include 展开，不截断在第 10 个**。每个节点含：被引用域、记录文本、`check_host()` 递归结果、是否计入预算。同时标出"第 11 个起收件方会停在这里（permerror）"的切点。
- 每条判定挂 § 号（§4.6.4 / §4.5 / §5.2 / §6.1 / §7）。

**验收**：
1. RFC 7208 测试集 **203 个用例通过率 ≥ 95%**，失败用例逐条登记在 `data/rfc7208-failures.md`（用例 id、期望、实际、原因、是否口径差异）。
2. 同一输入两次运行 `verdict.json` 字节级一致（`sha256` 比对）。
3. 断网环境跑 `mailvault audit` 成功（CI 有断网 job）。

---

### M2 DKIM 验签（对快照，不联网）

**依据**：RFC 6376 §3.4（规范化）、§3.5（`l=` 与正文长度）、RFC 8301 §3.2（<1024 位 RSA 必判无效）。

**输出**：`selector` / `d` / `i` / `a` / `c` / `bh` 是否匹配 / 失败位置（header 名 + 字节偏移或 body 第几行）/ `key_bits` / key 状态（`ok` / `revoked` / `missing` / `weak`）/ 结论与失败原因。

**验收**：
1. ≥ 5 类失败样本各有 fixture：body 被改、header 被改、`l=` 截断、key 缺失、key 过短（含 RSA-512）。
2. 无快照 key 时输出 **`undecidable`**，不是 `fail`。
3. 多签名（多个 `DKIM-Signature`）逐个出结果，不因一个失败短路。

---

### M3 DMARC 树走 + 对齐 + 处置

**依据**：RFC 9989 §4.10 / §4.10.1 / §4.10.2 / §3.2。

**输出**：
- 命中的是哪条 `_dmarc` 记录（Author → Org → PSD 顺序）。
- 树走路径 + 每跳查询结果（含 NXDOMAIN / 无记录 / 有记录但不合法）。
- `spf_align` 与 `dkim_align` **双算** relaxed 与 strict。
- `disposition`（`none` / `quarantine` / `reject`）。
- `psd` 归属、**PSL 版本与日期**、旧标签告警（`pct`/`rf`/`ri`）。

**验收**：
1. 复现 RFC 9989 Appendix B.4.1–B.4.3 三个 tree-walk 示例，输出逐跳与预期一致。
2. `pct=` 出现时给"已被 RFC 9989 删除"告警，**不得静默忽略**。
3. `psd=y` 与 `np=` 的归属判定有独立 fixture。

---

### M4 三方对账

**对象**：报文中的 `Authentication-Results` / `Received-SPF` / `Received` 链 **vs** M1–M3 在同一快照上的重算结果。
**依据**：RFC 8601 §2.5 / §4.1 / §5 / §7.1、RFC 5321 §4.4、RFC 5322 §3.6.7。

**输出**：三分类——`一致` / `矛盾` / `无法判定`；外加 Received 链单调性与时钟回退检测。

**硬性要求**：
- **每条矛盾必须给"两种可能解释 + 各自验证方法"**（例：转发导致 SPF fail vs 信封被改写；给出分别要查什么）。
- `--strict-evidence` 下**不得出现"攻击/伪造"字样**，只能出现"与重算不一致，可能解释为 A 或 B"。
- authserv-id 不可解析时按 authres_status #86 的教训处理：**fail-closed，判 `无法判定`**，不得当成有效证据。

**验收**：≥ 3 个 fixture：① 转发器 SPF fail 但 DKIM 过；② 网关重写正文导致 `bh` 不匹配；③ 注入伪造 `Authentication-Results`。

---

### M5 what-if 反事实 + RUA 关联（最小版）

**候选变更**：`p=none` → `quarantine` / `reject`；`~all` → `-all`；加 `include:`；加 `t=y`。
**做法**：只重跑 M1–M3 并做**差分**（不重写求值器）。
**RUA 关联**：输出"上 `p=reject` 会打断谁"（按报告里的 source IP / 域 / 对齐结论聚类）。

**验收**：
1. 差分可复算：同一输入两次运行一致；差分结果能反推出基线。
2. 输出明确标注：**只覆盖报告期内且依赖报告方口径**。
3. 无 RUA 数据时输出 `undecidable` 与该功能所需的输入清单，不猜。

---

### 扩展项（首期做接口预留，不阻塞验收）

- 完整 Received 时钟/顺序分析（多跳、乱序、跳数异常）。
- SRS 影响模拟（只模拟对 SPF 与对齐的影响，不实现 SRS）。
- ARC 辅助证据（只报链是否密码学完整；标 Experimental）。

## 6 含金量锚点

### 6.1 三工具边界（✅ 实测/读文档）

`mailauth` 已离线重放 + 已支持 RFC 9989 tree walk；`checkdmarc` 不做 `check_host()`、CLI 无离线输入、不读 `.eml`、不验 DKIM；`pyspf` 有完整 `check_host()` 与 203 用例测试集但无 CLI/无 DMARC；`dkimpy` 可注入 DNS 但纯库；`parsedmarc` 只解析报告。**空白在于"同一快照上的三方对账 + 条款账本 + 求值轨迹"。**

### 6.2 需求原话（✅）

见 2.2。核心是"配置看起来都对，结果还是不对"，且现有工具只给片段事实。

### 6.3 RFC 条款（✅）

见 2.4，均已核对原文，可直接在账本中引用。

### 6.4 开源空白（⬜ 软论据）

### 6.5 灰区（✅ 已识别）

见 2.5。五条灰区全部落到 `undecidable` 语义与输出字段上。

### 6.6 受众

自建邮件服务器运维、邮件服务商/ESP 的交付工程师、MSP、需要留档的安全团队。

### 6.7 时代性

RFC 9989（DMARCbis）刚落地，`pct`/`rf`/`ri` 转 historic、`psd`/`np`/`t` 新增，存量工具与文档滞后明显；"新标准 + 可复算账本"的时间窗真实存在，但**不宽**（见 00-README 风险 ②）。

### 6.8 开源空白三行

- 记录级检查（checkdmarc 类）成熟，报文级判定（mailauth/pyspf/dkimpy 类）成熟。
- 报告解析（parsedmarc 类）成熟，可视化（dmarc-visualizer 类）成熟。
- **三者交叉对账 + 条款账本 + what-if 差分：检索窗口内最高 1★（`spf dmarc audit report in:description` 16 个仓库全 0–1★）。**

## 7 边界与非目标

**明确不做**：

- **不承诺进箱**，**不做垃圾评分**。mail-tester 类服务需真实发信且分数不可复算，列为"不做"。
- 不做远程 DNS 扫描以外的扫描（本工具连远程扫描都不默认做，`snapshot fetch` 是显式一次性动作）。
- 不做 SRS 实现（只做影响模拟）。
- 不做 SPF flatten（已有 31 仓、头部 43★，赛道已满）。
- 不做 DMARC 看板可视化（781★ 已占）。
- **不把 ARC 当主卖点**（Experimental，且拟转 Historic）；只作辅助证据。
- 不输出"进箱概率"、不给内容打分、不评价发信声誉。

**红线**：

- **隐私红线**：审计阶段零网络；快照与 `.eml` 均本地；不内置遥测、不回调、不上传。
- **品牌隔离**：本仓库与同系列其它项目互不提及、不交叉引用、不共享品牌元素。
- **首期范围限定**：M1–M5 最小闭环 + 扩展项接口预留；超出范围的需求进 `docs/backlog.md`，不临时扩范围。
- **可解释性红线**：每条矛盾给两种解释 + 验证方法；`--strict-evidence` 禁用"攻击/伪造"字样。
