## 2 真值纪律

### 2.1 真值只存"输入 + 期望"，不存推导过程

`expected.json` 的形状固定为：

```json
{
  "case_id": "spf-include-nested-01",
  "input": {"snapshot": "snap.json", "query": "query.json", "eml": null},
  "expect": {"spf.result": "pass", "spf.budget.terms.used": 3},
  "why": "RFC 7208 §5.2：include 对子域做 check_host，子域 -all 不终止父域"
}
```

- `input` 只指文件，不内联内容（内联会与 fixture 本体漂移）。
- `expect` 用**点路径 → 值**，只登记会被判定的字段。
- `why` 必须能追到条款或明确的项目口径；**没有 `why` 的真值条目视为无效**。

### 2.2 期望值必须能由输入独立复算

每类真值配一条**独立复算**路径：

| 真值类别 | 独立复算方式 |
|---|---|
| SPF | pyspf 的 `check_host()` 作为参照实现（仅测试期，不进运行时依赖）跑同一份合成快照 |
| DKIM | 用 `cryptography`（仅测试期，装在 `dev` extra）独立签/验；另用 dkimpy 1.1.8 逐条对账（见 §3.3） |
| DMARC | 手算对齐域（relaxed = 取 Organizational Domain 比对；strict = 逐字比对）；另用 RFC 原文写死的期望（B.4.1–B.4.3 的逐跳查询序列、§4.10.2 三个 Org 选择例子、§4.4 Table 1 三行）作为不依赖实现的真值 |
| 对账 | 人工构造的矛盾点写进 `why`，断言必须能定位到同一处（M5：另加一张**手算的分类真值表**，见 §3.5） |
| what-if | 与**另一次独立运行**的 `audit` 产物比对：`apply_ops(candidate, invert(ops)) == audit 的账本`。不是"跑两次 whatif 看一样"——那只证明确定性，不证明**可逆性**（见 §3.5） |

**关键**：参照实现只用于**测试期对账**，生产代码不得 import 它（AST 守门，M2 落地）。

### 2.3 缺口不补编

快照里没有的 DNS 记录、报文里没有的头，**不得为了"让样例跑通"而补造**。
缺数据 → `undecidable` + `warnings` 写明缺什么。这条与题面 §2.5 的灰区纪律同源。

### 2.4 抽样 ≠ 全量

任何"看起来都对"的判据必须**全量复核**。例：把 203 条 RFC 用例里的 `expect` 逐条与 pyspf
参照实现比对，而不是抽 10 条手工看。抽样的结论只证明"抽到的那几条长这样"。

### 2.5 生成器的幂等性

凡有生成器（`tools/gen_*.py`）产出的数据：

- `--check` 模式必须重生成后**逐字节比对**已入仓文件；
- 部分运行（`--only` / `--suite`）**不得**改写全量清单；
- CI 里跑 `--check`（本地等价校验，首次推送前无 CI）。

## 3 数值口径（唯一出处 = `mailvault/constants.py`）

下表列的是**语义与条款**；`数值` 一列在代码里只出现一次，其它位置只能引用常量名。

| 口径 | 常量名 | 值 | 条款 | 超限后果 |
|---|---|---|---|---|
| SPF term 上限 | `SPF_MAX_TERMS` | 10 | RFC 7208 §4.6.4 | 第 11 个 → `permerror`（MUST） |
| MX 机制单次上限 | `SPF_MAX_MX` | 10 | RFC 7208 §4.6.4 | `permerror`（MUST） |
| PTR 机制单次上限 | `SPF_MAX_PTR` | 10 | RFC 7208 §4.6.4 | 超出前 10 条**被忽略**（截断），**不是** permerror——见 §3.1 更正 | 
| void lookup 上限 | `SPF_MAX_VOID` | 2 | RFC 7208 §4.6.4 | 超限 → `undecidable` + 告警（原文是 SHOULD，**不硬判 fail**）；同记录若另踩 MUST 级限制则报 MUST |
| 嵌套深度上限 | `SPF_MAX_DEPTH` | 20 | 本项目第二道保险 | 超限 → `permerror`（防递归栈跑穿） |
| 树节点数上限 | `SPF_TREE_MAX_NODES` | 256 | 本项目 | 只影响 `tree` 诊断输出，**不影响判定** |
| 每条矛盾的最少解释数 | `RECONCILE_MIN_EXPLANATIONS` | 2 | 题面 §3 的 M4 硬性要求 | 少于 2 → `InternalError`（不变量写进代码） |
| RSA 最小位数 | `DKIM_MIN_KEY_BITS` | 1024 | RFC 8301 §3.2 | 低于 → `fail`（MUST） |
| 快照 schema 版本 | `SNAPSHOT_SCHEMA_VERSION` | 1 | 本项目 | 不匹配 → exit 3 |
| 账本 schema 版本 | `LEDGER_SCHEMA_VERSION` | 1 | 本项目 | 不匹配 → exit 3 |
| 退出码 | `ExitCode.*` | 0/1/2/3/4 | 题面 §3 | 见 `exits.py` |
| 结果枚举 | `RESULTS` | 见 `plan/03` K4 | RFC 7208 + 本项目 | 未知值 → 内部错误 |

**禁止**：把星数、下载量、issue 数、检索总数写成常量或默认输出（题面 §5 扣分红线）。
这些数字只存在于 `data/README.md` §1–§2 的"检索窗口快照"里。

### 3.1 M2 实测后更正的 SPF 口径（以 RFC 7208 原文为准）

三条早期表格里写得不准，M2 逐条核对原文后更正。更正**同时**落在这里、代码注释与
`tests/test_spf.py` 的断言里——只改代码不改表，下次读表的人会以为代码写错了。

| # | 早期写法 | RFC 7208 原文 | 本项目实现 | 佐证 |
|---|---|---|---|---|
| C1 | PTR 超限 → `permerror`（MUST） | §4.6.4："If this limit is exceeded, **all records other than the first 10 MUST be ignored**"；§5.5：此时 `ptr` 机制按**未匹配**处理 | **截断到前 10 条** + `warnings` 写明截断了几条 | 上游用例 `Processing limits/ptr-limit` 期望 `neutral`/`pass` |
| C2 | void 超限 → `permerror` | §4.6.4："SPF implementations **SHOULD** limit 'void lookups' to two" | `undecidable` + 告警（题面 §2.5 灰区 2）；**但**同记录若另踩 MUST 级限制，报 MUST | 上游用例 `void-over-limit` 是本棒**唯一**的已登记口径差异 |
| C3 | `%{p}` 缺 PTR → 默认 fail | §7.3："the result is the string `unknown`" | 展开仍按 §7.3；只有**由含 `%{p}` 的机制匹配决定结果**时才降级为 `undecidable` | 上游用例 `p-macro-ip4-novalid` 等期望 `fail`（`%{p}` 用在 `exp=` 文本里） |

> **C1 与 C2 的差别为什么存在**：RFC 明说 MX 数据归**发布方**控制（可以要求发布方修，
> 所以 MUST 级 permerror），PTR 数据归**连接 IP 的所有者**控制（不能因别人的数据判你坏，
> 所以只能截断）。这两条看起来"不一致"，其实是协议有意的分工。

**参照实现对照**（`plan/04` §2.2 的"独立复算"）：用 pyspf 2.0.14 跑同一份 203 条，
203/203 全通过。说明本项目那 1 条失败不是夹具不全或桩语义错，而是刻意的口径选择。
逐条登记见 `data/rfc7208-failures.md`。

### 3.2 M3 实测：DKIM 与参照实现的 2 条口径差异（以 RFC 原文为准）

`fixtures/dkim/` 的 11 个用例逐条跑 dkimpy 1.1.8（每例单独 `verify(idx=i)`）对账，
**9 例一致、2 例有意不同**。两条都按 RFC 判，不按参照实现判：

| # | 参照实现 dkimpy | RFC 原文 | 本项目实现 | 佐证用例 |
|---|---|---|---|---|
| D-C1 | `l=` 大于规范化正文长度时静默 `body[:l]` 取全量，签名仍可能 pass | RFC 6376 §3.5："This value **MUST NOT** be larger than the actual number of octets in the canonicalized message body"；§6.1.1：任何 "inconsistent or unexpected values" 立即 PERMFAIL (signature syntax error) | `permerror` + `failure_at.kind=length_exceeds_body` | `d3b-length-exceeds-body`（dkimpy=True，本项目=permerror） |
| D-C2 | `a=rsa-sha1` 照算密码学结果并可能判 True | RFC 8301 §3.1："rsa-sha1 **MUST NOT** be used for signing or verifying"；§3 收尾：这类签名 "have permanently failed evaluation" | `permerror` | `tests/test_dkim.py::test_rsa_sha1_is_permerror_per_rfc8301` |

**其余 9 例逐条一致**（`tests/test_dkim.py` 用 fixture 断言，不靠人工比对）：
正样本 pass、body 改 fail、header 改 fail、`l=` 截断 pass、key 未查 undecidable、
key NXDOMAIN permerror、RSA-512 fail、多签名 `[fail, pass]`、未签名 none。

**为什么这两条差异值得留**：它们不是实现偏好，是 RFC 8301 更新后的**协议结论**。
跟 dkimpy 会让本工具对"已永久失败的签名"报 pass——那正是账本最不该犯的错。
若用户反馈要跟 dkimpy，须同时改 `gen_dkim_fixtures.py`、`dkim.py`、测试与本表（`plan/06` G11）。

### 3.3 M4 实测：DMARC 的域映射与"真值从哪来"

**域映射（卫生门 K11 的代价）**：RFC 9989 Appendix B.4.3 用 `giant.bank.<保留 TLD>` 做示例，
其 TLD 不在卫生门白名单（只认 `example.com` / `.net` / `.org` / `.invalid` 及其子域）里。
处置是**把示例整体落到 `.example.com` 下**，而不是放宽卫生门——每放宽一次，
"fixture 引用了真实域名"这条红线就少一道护栏。每个 `expected.json` 的 `why` 里写明
这是映射形态。

**真值三层（逐层回答不同问题）**：

| 层 | 真值来源 | 锁住的是 |
|---|---|---|
| 1 | RFC 原文写死的**逐跳查询序列**（B.4.1–B.4.3）与 **Org 域选择例子**（§4.10.2 三个） | 走查实现写对了 |
| 2 | `fixtures/dmarc/*/expected.json`（6 例，4 pass / 2 fail / 2 种处置） | "输入 → 结论"这条链路 |
| 3 | **独立手算**的 Organizational Domain（自写 min-by-labels，不共享 `dmarc.py` 代码） | 对齐结论与独立实现一致 |

第 1 层最关键的一条：**B.4.2 的跳步**。13 标签 Author 的第 2 跳必须直接落到 7 标签处
（原文 "skipping the intermediate names"），全程 8 次查询。漏掉跳步的实现会逐级爬，
`walk[1].qname` 与 `walk_queries` 两条断言会同时变红——这是"逐跳"而不是"最终结论"
能被证明的地方。

**`psd=y` 与 `psd=n` 必须给出不同答案**：B.4.3 的 `psd=y` 让 Organizational Domain 变成
记录所在域的**下面一层**；`psd=n` 则**就是**记录所在的域。`fixtures/dmarc/psd-n/` 与
`b43` 各证一侧，`test_dmarc.py::test_psd_y_and_psd_n_produce_different_organizational_domains`
用同一份快照只改 `psd=` 取值做对照——两个标签被当成同一件事时立刻变红。

**`np=` 的样本必须让 `sp=` 与 `np=` 取值不同**：否则"用错了哪个标签"看不出来
（两者都是 `quarantine` 时，选错也判对）。`fixtures/dmarc/np/` 用
`sp=reject` / `np=quarantine`，处置差异直接可见。

**为什么不引 DMARC 参照实现**：`plan/04` §2.2 对 DMARC 的定义就是"手算对齐域"，
不是引第三方库。理由：能算 tree walk 的库（checkdmarc / mailauth）各有自己的 PSL 与
`psd` 口径，拿它们当"真值"会把它们的口径当成标准——而 RFC 9989 §4.10 的走查是**新**
算法，库跟得不齐时反而更难分辨谁错了。所以这一层靠原文 + 手算，不靠库。

### 3.4 两套时间线不要混

- **产品版本**（`__version__`）：管代码，`v1.0.0` 由 M6 定版。
- **规则集/schema 版本**（`SNAPSHOT_SCHEMA_VERSION` / `LEDGER_SCHEMA_VERSION`）：管判定口径。
  判别 = **"这次改动会让旧报告失效吗？"** 会 → 升 schema 版本 + 写迁移说明。
- `DIFF_SCHEMA_VERSION`：管 `diff.json`。它**不是账本**（没有 `ledger_id`、没有
  `summary.exit_code` 的判定含义），所以不复用账本版本号——两套时间线混用会让
  "账本 schema 变了"与"差分报告 schema 变了"两件事互相假装。

### 3.5 M5 实测：对账与 what-if 的"真值从哪来"

**对账的真值是三层，逐层回答不同问题**：

| 层 | 真值来源 | 锁住的是 |
|---|---|---|
| 1 | **手算的分类真值表**：`_hand_class()` 独立重写一遍"可信 + 两侧可比 → 相等则一致、否则矛盾"的规则，与模块输出逐条比对 | 分类逻辑写对了 |
| 2 | `fixtures/reconcile/*/expected.json`（3 例，含 3 条 `consistent` / 1 条 `contradiction` / 4 条 `undecidable`） | "输入 → 结论"这条链路 |
| 3 | **反自证**：三分类必须**都有**样本；矛盾必须 ≥2 解释；矛盾**不得**折成 `fail`；禁词自检位必须能真的变 false | 这套测试自己不会永远绿 |

第 3 层不是形式主义：一个"永远返回同一分类 + 两条模板解释"的实现能通过第 1–2 层，
只有"三分类都要有样本"把它按住。`r1-forwarded` 专门提供 `consistent` 一侧。

**矛盾点的可定位性**：`r2-gateway-body` 的 DKIM 侧是**真签名**——对 `ORIGINAL_BODY` 签，
再把报文正文换成 `GATEWAY_BODY`（尾部多一行网关声明）。于是失败点精确落在
`failure_at.kind == body_hash`，而不是"签名头语法错"。手写签名头只会得到
`header_syntax`，`bh` 不匹配这条路径永远走不到。`expected.json` 的 `why` 把这条
构造关系写全，断言能定位到同一处。

**what-if 的"真值"是另一次独立运行的 `audit`**：`whatif` 的差分 ops 反转后施加到候选账本，
必须**逐字节等于** `audit` 在同一份未改输入上的产物（含 `ledger_id`）。
只跑两次 `whatif` 看字节一致，证明的是确定性；**可逆性**必须靠"与另一个入口的产物对账"。

**RUA 报告的筛选口径被真实数据钉住**：`rua.json` 三条记录里只有一条 SPF 与 DKIM
**都**没通过。改成"任一不过就算会被 `p=reject` 打断"会把数量从 1 变 2，测试立刻变红
（`test_rua_fixture_clusters_the_senders_that_reject_would_break`）。一条"看起来对"的
聚类规则必须有能区分它的样本，否则它只是措辞。

### 3.6 M5 的一处守门判据改动（卫生门）

对账 fixture 里出现 RFC 8601 §2.2 的 **ptype 关键字** `smtp.mailfrom=`。它的形态与两级域名
无法区分（`smtp.mailfrom` 的"TLD"是 8 个字母，落在 `DOMAIN` 正则的 2–24 区间里），
于是卫生门把协议关键字判成了"非保留域名"。

处置是给 `tools/check_fixture_hygiene.py` 加一条**结构性前缀剥离**：扫之前先剥掉
`(smtp|header|body|policy|dns).property=`。**这不是放宽判据**，理由与 `FILE_EXTENSIONS`
一致：

- 剥的是**整个 token**（`ptype.property=`），`=` 右边真正的域名照旧被扫到；
- ptype 是 RFC 登记过的**闭集**，不是"常见词白名单"（白名单会随文档增长而漏）；
- 配**阴性对照**：同位置换上真实域名必须报红
  （`tests/test_reconcile.py::test_hygiene_gate_strips_ar_ptype_but_still_catches_a_real_domain`，
  用的是测试临时目录，不把真实域名写进 `fixtures/`）。

**为什么不改 fixture 绕开它**：`smtp.mailfrom=` 是 RFC 8601 的真实属性名，删掉会降低
fixture 保真度（读者看不到"收件方当时评估的是哪个信封发件人"）；而"改数据去迁就门"
正是会让门慢慢失去意义的那种操作。

## 4 数据落库检查清单（每个 fixture 入库时逐条过）

- [ ] 域名只用 `example.invalid` / `example.com` / `example.net` / `example.org` 或 RFC 2606 保留名
- [ ] IP 只用 `192.0.2.0/24` / `198.51.100.0/24` / `203.0.113.0/24` / `2001:db8::/32`
- [ ] `.eml` 里没有真实 `Message-ID` / 真实邮件地址 / 真实时间戳
- [ ] 密钥文件带"仅 fixture 使用，不得用于生产"的说明
- [ ] `snap.json` 的 `resolver` 字段为 `synthetic`，`fetched_at` 为合成时间
- [ ] 若文件字节被 sha256 登记 **或字节本身就是被测对象** → `.gitattributes` 标 `-text`（防克隆时归一化）
- [ ] `expected.json` 每条 `why` 可追到条款或项目口径

> 最后一条第二条是**容易漏的**：`.gitattributes` 的 `* text=auto eol=lf` 会把 CRLF 归一，
> 凡"字节形态本身是被测对象"的文件（CRLF 变体样张、登记过 sha 的快照）都必须 `-text`。
>
> **M5 实测：`.eml` fixture 漏了这条，后果只在克隆后才显形。** 实测（临时 bare 仓库
> round-trip）：不带 `*.eml -text` 时，`git add` 把报文里的 25 处 CRLF 归一成 0 处，
> 于是**裸 clone** 起来的 fixture 让四个生成器的 `--check` 全部报
> `message.eml 字节不一致`、DKIM 验签全变 `body_hash` 失败；补上该规则后克隆出来的
> 字节与生成器产物逐字节一致、全绿。
> 这条故障**在本机工作区看不出来**（文件没被 git 碰过），所以另加一条断言
> `tests/test_determinism.py::test_eml_fixtures_need_crlf_and_must_be_declared_minus_text`
> ——它同时断言"fixture 里真有 CRLF"与"`.gitattributes` 里真有 `*.eml -text`"，
> 缺一半都不算守住。这是 M6"干净环境（裸 clone 直跑）"的前置条件。

### 4.1 豁免登记（K11 的逐条例外，M1 起生效）

`tools/check_fixture_hygiene.py` 的默认判据是"保留域 + 文档 IP 段"。**唯一的两条例外**
是上游原样件，登记在脚本的 `EXEMPT_FILES` 里，且脚本输出会打印"豁免了哪几份、为什么"：

| 文件 | 豁免理由 | 若改写的后果 |
|---|---|---|
| `fixtures/spf/rfc7208-tests.yml` | 上游 `CHANGES` 自述 "I was stupid to use 1.2.3.4 - that is a real global IP"，属历史遗留；文件字节即"上游哪一版"的证据 | 203 条用例的输入与期望一起漂移，测试集不再是上游那一版 |
| `fixtures/spf/rfc7208-tests.LICENSE` | 许可第 1 条要求保留原始版权声明，声明含作者域名 | 违反上游许可 |

**豁免的边界**：只到这两份文件本身。任何其它 fixture（含本项目自建的 `snap.json` /
`message.eml` / `expected.json`）引用真实域名或非文档 IP 段，门依然报红。
"豁免"不是"关掉这一条"——判据仍然逐行扫描这 5 份自建 fixture。

## 5 目录约定

```
fixtures/
├─ spf/        RFC 7208 测试集 + 预算/树的样例
├─ dkim/       五类失败样本 + 测试密钥
```

每组至少：`README.md`（这条 fixture 证什么）、输入文件、`expected.json`。

**M5 的两组都由生成器产出**（`tools/gen_reconcile_fixtures.py` /
`tools/gen_whatif_fixtures.py`），`--check` 逐字节幂等。理由与 M3/M4 相同：
"对账的期望分类"与"报文头里声称什么"必须放在同一处，手改必然漂移。
